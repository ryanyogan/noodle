# Nudges are recorded and read in the bell

A Nudge used to exist only as a notification on a device: once dismissed it was gone, and a Parent without Nudges on for any device never got one. The bell (#157) lists, for the signed-in Parent, the releases of the Changelog they haven't seen and the Nudges sent to them, newest first, each leading where the Nudge or the release leads. A Nudge is recorded when the Household Agent sends it; a device is one way it reaches a Parent and the bell is the other.

## Consequences

- **Recorded when sent, per Parent.** `sent_nudges` has one row for each Parent a Nudge goes to (Household, Member, kind, title, body, url, sent at), written by the Agent's alarm as it hands the due Nudges to the Queue: after that Parent's quiet hours, with the words made for that Parent. It is written after the Queue has them, so a run that fails there and is retried sends a Nudge again (a device shows it once, by its tag) rather than recording it twice. Rows older than 60 days are dropped as new ones are written.
- **Every Parent is someone a Nudge could go to**, with a device for Nudges or without (`loadNudgeRecipients` no longer asks for a push subscription). Preferences and quiet hours apply as before; the Queue finds no device and delivers nothing; the bell has the row. So the Agent now looks at a write even in a Household where nobody turned Nudges on.
- **Privacy (ADR-0003) is unchanged because nothing is read again.** A Nudge about a Personal Allowance is only ever made for its owner, and a Quick Add's is made from what `visibleTo` let that recipient read; the row keeps exactly those words for exactly that Member, and `loadBell` reads by the Member of the session. No row is shared between Parents.
- **Not recorded:** the test Nudge (a Parent sent it to themselves), and "Noodle was updated", which the bell says as the release itself (`NUDGES_NOT_RECORDED`). An update that brings no release makes no row.
- **Releases aren't stored.** They are the Changelog's, read when the app is built; a release is a row of the bell until the Parent has seen it, and after that it is in the Changelog. A read Nudge stays listed (the latest 20 rows), so one dismissed on a device can be found again.
- **Read state is on the server, per Parent** (`bell_seen`), so the phone and the computer agree. It is two marks, not one timestamp: Nudges sent up to a moment, and releases up to a release's day. A release has only a day, and with one timestamp a release going out in the afternoon would count as read by a Parent who opened the bell that morning. Opening the bell sends the marks of what it listed; they only move forward; the Parent's other screens are told through the Household Agent (`bell`).
- **A Parent with no mark yet** (everyone on the day this shipped, and each new Parent) has read every release but the latest: nobody is met by the whole Changelog (`startingBellSeen`).
- **The update Nudge leads to the Changelog** when the update brought a release the Household wasn't told of: it names the release ("New in Noodle: …") and opens it. The Agent remembers the day of the release last told beside the build. An update with no new release says "Noodle was updated" and opens This Month, as before.
- **Where the bell is.** There is no header shared by every page: on a computer the bell is in the Sidebar's head (under the trigger in the rail); on a phone, where a page's header takes one action and nothing sits above the title (#74), it is the first row of More, and More's tab carries a dot while something is unread.
- Neither table is in a snapshot (what was sent isn't unsent by a restore); a Fresh start and deleting the Household clear both.
- The pure part (`bell` in `packages/domain`) says what is listed and unread from the marks, the releases and the Nudges.
