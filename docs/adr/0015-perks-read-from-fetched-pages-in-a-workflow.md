# Perks are read from fetched pages, in a Workflow, and must quote them

A Perk Source's Perks come only from a web page the Worker fetches: the catalog's benefits page for a well-known product (`PERK_SOURCE_CATALOG` in `@noodle/domain`), or one a Parent links. The model (`AI_MODELS.reason`, ADR-0012) is told to read that page's text and nothing else, and to copy for each Perk up to twenty words of the page that say so. Plain code (`perksOnPage`) then keeps only Perks whose quote, and whose service or cost, really appear in the page's text. So a Perk the model remembers from training, or half-remembers from an older version of the plan, never becomes a Perk. Each stored Perk carries the page it came from and the day it was read, and the screen shows both.

When the page offers tiers whose Perks differ and the Perk Source's plan isn't known, research stores the tiers and asks the Parent which plan they have (`perksForPlan`), rather than guessing the cheapest or the richest. The model never states an amount the app uses: a Perk Overlap's figure comes from the Household's own Commitments and Transactions (ADR-0012's rule that money stays in domain code).

Research runs in the Perk research Workflow (`PERK_RESEARCH`), one instance per run: when a Parent confirms or adds a Perk Source, picks its plan, links a page or asks to check again, and from the nightly cron for Perk Sources last read 30 days ago or more (one instance per source per day, so a re-run cron adds nothing). Fetching and reading are separate steps with their own retries, so a flaky site or a busy model doesn't lose the other's work; out of retries, a 4xx, or a page with next to no text (one only a browser renders) marks the Perk Source "unreadable" and the Parent can link another page. The Perks it had are kept until a read succeeds. A finished read looks for Insights at once, so a Perk Overlap shows without waiting for the night. With the fakes (AI_MODEL=stub), research runs inline in the Parent's request, which is how E2E sees it.

Perk Sources seen only in a Parent's own Personal Allowance are theirs alone, like Insights (ADR-0003), and so are their Perks and the Overlaps resting on them. Detection is plain code over spending, Commitment names and Account names, matched to the catalog; nothing is sent to a model to find them.

Considered: letting the model answer from what it knows (fast, but stale or invented Perks with no source, which a Parent can't check), a search API to find each product's page (another vendor and key, and search results are no better a source than the product's own page), and Browser Rendering for pages built by script (kept as a follow-up: a Parent can link a readable page meanwhile).
